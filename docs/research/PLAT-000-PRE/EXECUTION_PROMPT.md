### 2. 必须遵守的判断规范

对用户、其他 AI、README、官网和旧报告均检查前提是否成立、推理是否跳步。

- 主动指出遗漏变量、学习成本、依赖成本、改造成本、许可成本、升级成本及退出成本。

- 不把所有既定架构手段都当成不可讨论的产品硬要求，也不自行改变已批准基线。

区分：
VERIFIED_FACT：可核验事实，附来源。
DESIGN_DECISION：有理由和代价的建议，尚未被用户批准即不能执行。
ASSUMPTION：明确假设及验证方式。
UNVERIFIED：尚未证明，不作为通过依据。

没有依据时，不给出“覆盖 90%”“节省 80% 开发量”“几天完成”等伪精确数字。范围、工期和成本估算须注明假设与证据，优先给出具体改造工作包。

### 8. 深读关键实现，而不是复制功能表

对入围候选追踪以下真实链路，并给出文件、类/函数、调用关系和边界：

A. 新建对象/字段 → 元数据保存 → 物理结构变化 → API/页面生效。
检查实际是运行时解释、运行时代码生成、构建时代码生成，还是固定对象加 JSON/EAV 属性。JSON/YAML/XML 文件的存在本身不能证明运行时动态能力。

B. 业务请求 → 身份 → 对象/字段/记录权限 → 查询/Action → 事务 → 审计/事件。
检查管理员绕过、服务账号、后台任务和批量接口的权限语义，不能只看前端按钮隐藏。

C. 元数据变更 → 依赖检查 → 发布/迁移 → 存量数据 → 缓存/索引失效 → 失败恢复。
区分 Git 保存配置与生产配置发布治理；二者不是同一能力。

D. Action 定义 → 输入输出 Schema → 前后端调用 → MCP 暴露。
区分 MCP Client 与 MCP Server，区分少量固定工具与动态注册，区分通用 OpenAPI 包装与具体用户委托执行。
无原生 MCP 不是自动淘汰理由；若统一 Action/Schema/权限接口适合局部适配，说明扩展路径。反之，不得用“加一层 MCP 很简单”掩盖缺少执行内核的问题。

E. 插件/扩展点 → 业务包 → 上游升级。
至少指明真实可用的扩展接口和现有使用例子。不能只说“支持插件”。评估定制是否会侵入存储、权限、发布和渲染核心。

F. UI 与日常业务体验。
检查主明细、批量编辑、默认值/依赖显隐、错误定位、中文、多语言和组件复用。无需本轮重做 UI，不用截图颜值代替可用性验证。

### 9. 使用双维度矩阵，避免把宣传当实现

对每个关键要求同时标注：

能力提供方式：
- COMMUNITY_NATIVE：明确的社区代码能力。
- OFFICIAL_COMMERCIAL：官方收费模块/版本。
- CUSTOM_EXTENSION：可通过已识别扩展接口补齐，尚待开发。
- CORE_REWRITE：需深入修改/重写核心。
- UNSUPPORTED：有证据表明当前版本不支持。
- UNKNOWN：证据不足。

证据级别：
- DOC_ONLY：只读到官方文档。
- SOURCE_TRACED：已追踪关键源码路径。
- EXISTING_TEST_FOUND：找到相关测试，但未必实际运行。
- RUNTIME_VERIFIED：实际执行了标明范围的验证。
- BLOCKED：网络/权限/环境阻碍了验证。

“社区原生”与“运行验证过”是两个不同维度，不可相互替代。

如采用评分，先公开维度、权重和未知值处理规则，保留硬性阻断项；不能用 UI、Stars 等加分抵消许可证或权限模型问题。本轮优先使用逐项证据与改造工作包，不强求总分。

### 10. 必要时执行小而决定性的运行验证

默认先静态尽调，不为所有项目搭演示，也不自建两套新平台。

只有决定性疑点才选 1—2 个合法可运行候选做最小试验。试验问题要提前写清；通过试验也不代表已完成平台验收。

建议场景：
1. 在运行系统中配置采购申请主对象与明细对象，检查是否需要新建对象专属代码、重启或重新部署。
2. 创建真实数据并查看实际存储结构；调用自动生成的数据 API。
3. 用两个身份验证一项记录/字段授权的正反例，不能只用超级管理员。
4. 增加字段后检查已有记录，尝试配置导出/导入另一隔离实例；不可用的步骤记录原因。
5. 有原生 MCP/Action 时检查 Schema 与身份；没有则仅检查适配接口，不临时写完整 MCP 来替候选补分。
6. 可行时做一个独立小扩展示例，验证不改核心的主张；不能演变为完整定制项目。

可根据决定性问题缩小场景，但不能只用“容器启动/首页打开”证明整体适配。

只运行官方默认数据库时，不得声称已验证 PostgreSQL。使用开发分支、修改启动脚本或禁用模块时记录每处差异，区分原版能力与试验补丁。

未获取商业模块，不能臆造其源码行为。不开收费试用、不给信用卡、不调用付费模型 API；此类需求标记待定。

记录命令、时间/时区、退出码、源码 SHA、镜像 tag/digest、环境、请求/响应脱敏摘要、失败首因和清理方法。

若无法执行，保留静态结论，标记推荐的限制；不能将环境失败当功能失败，也不能将未跑的步骤写为 PASS。

### 11. 复用判断必须包含长期维护与退出成本

对首选及主要备选，明确哪些是：
- 直接采用，不改上游。
- 官方配置/业务包。
- 独立插件或外围适配。
- 受限补丁，需要持续跟踪上游。
- 大规模核心改写。

重点回答：
1. 为什么比自建内核更值得，具体省去了什么，而不只说功能很多？
2. 哪些缺口仍然要自己承担？
3. 是否需要换后端/前端/数据库？换栈的收益是否足以覆盖迁移和长期成本？
4. 用户要求的统一权限、事务、配置迁移能否在现有抽象中实现？
5. 自定义是否能通过稳定插件完成；升级时需要重放哪些补丁？
6. 核心维护减少、许可改变、商业模块停订阅时怎么办？
7. 能否导出元数据、数据、附件关系、流程/审批历史？导出格式能否支持迁出而不仅是备份？
8. 运维需要哪些服务、操作系统、构建工具、网络服务和人工角色？
9. 是否存在独特 DSL/框架使 AI 和后续人员难以调试？依据是什么？
10. 内部多个独立系统升级是否被强绑定？是否会逐渐产生无法合并的不同内核？

以清楚的工作包和风险解释成本；不得虚构授权报价、开发天数或生命周期收益。

优先选择“上游平台 + 独立 LCP 扩展包”，而不是“复制源码后长期随意修改”。若不得不深度 fork，必须提出明确的上游跟踪与升级策略，不能声称 fork 后就不再依赖上游维护能力。

### 12. 输出四种路线之一，不预设结论

结论类型：

REUSE_PLATFORM：有值得采用的整个平台候选，说明确切版本、缺口、授权条件、改造方案和待验事项。此状态是建议，不是采用授权。

COMPOSE_COMPONENTS：无合适整平台，但有明确可独立复用组件；说明组件边界与许可，不把不同平台的数据库、权限与流程内核直接拼成一套。

BUILD_CORE：在本次已说明的搜索范围和证据下，没有足够适配的整平台，建议按现有技术路线自建核心，仍复用成熟基础组件。

INSUFFICIENT_EVIDENCE：关键来源/许可/代码/环境不可访问，尚不能合理推荐或排除；给出最小补证需求。

不能把有限搜索写成“世界上不存在符合要求的项目”。如果首选不符合已批准技术栈，另附待批准 ADR，不能因此自动更改基线。

任何结论都不触发下一模块开发。最终交给用户与 ChatGPT 审查，批准后再给采用/改造或恢复骨架的正式 Prompt。

### 14. 研究成果的 Git / GitHub 交付

先检查原工作区，不能假定已有 main、origin 或用户身份。

已有 LCP 仓库：从明确基线创建 research/plat-000-pre-oss-selection，保留既有代码和其他工作。
